# Brainstorming Skill

> **编码前强制结构化构思** —— 一次一问，多方案对比，输出设计文档

---

## 核心原则

| 原则 | 说明 |
|------|------|
| **一次一问** | 不要一次性抛出一堆问题。每次只问一个问题，等回复后再问下一个。 |
| **先了解再设计** | 先探索代码库了解现有实现，再设计方案。 |
| **YAGNI 彻底** | 从所有设计方案中强制移除不必要的功能。能用简单方案就别搞复杂。 |
| **至少 2-3 方案** | 总是提供多个方案对比，附上权衡分析。 |
| **增量验证** | 分段展示设计（每段 200-300 字），每段后确认。 |
| **输出到文件** | 设计完成后，强制写到 `docs/plans/` 目录并提交。 |

## 核心能力

| 能力 | 说明 | 输出格式 |
|------|------|----------|
| **约束提取** | 从需求中识别显性和隐性约束 | 约束清单 |
| **方案生成** | 2-3 种实现方案（简单/平衡/复杂） | 方案卡片 |
| **边界分析** | 每种方案的边界情况和失效模式 | 风险矩阵 |
| **决策矩阵** | 多维度对比评分 | 对比表格 |
| **推荐决策** | 根据约束给出明确推荐 | 决策说明 |
| **设计文档输出** | 保存到 `docs/plans/` 并提交 | Markdown 文件 |

## 工作流程

### Phase 0: 代码库探索（新增）

在开始设计之前，先理解现有代码：

```markdown
1. 探索与需求相关的现有代码和模式
2. 查找类似的已有实现
3. 理解现有架构约束
4. 输出探索发现摘要
```

### Phase 1: 约束提取

**输出模板**：
```markdown
### 约束条件

| 类型 | 约束 | 来源 |
|------|------|------|
| 硬性约束 | ... | 需求明确指定 |
| 隐性约束 | ... | 团队技术栈/经验 |
| 资源约束 | ... | 时间/人力/预算 |
| 质量约束 | ... | 性能/安全/可维护 |
```

**一次一问原则** → 不要一次性问完所有约束。先问最重要的 1 个问题，等回答再继续。

### Phase 2: 方案生成（2-3 个方案）

**必须包含**：
1. **简单方案** —— 最快实现，满足核心需求
2. **平衡方案** —— 兼顾速度和质量
3. （可选）**复杂方案** —— 完整实现，考虑扩展性

**YAGNI 检查**：
- 每个方案列出「包含的功能」→ 问自己：这个功能真的需要吗？不 → 删掉
- 各方案之间对比时标注「复杂度增量」

**输出模板**：
```markdown
### 方案对比

| 维度 | 方案 A（简单） | 方案 B（平衡） | 方案 C（复杂） |
|------|---------------|---------------|---------------|
| **核心思路** | 一句话描述 | 一句话描述 | 一句话描述 |
| **开发时间** | X 天 | Y 天 | Z 天 |
| **维护成本** | 低/中/高 | 低/中/高 | 低/中/高 |
| **扩展性** | ⭐⭐⭐ | ⭐⭐⭐⭐ | ⭐⭐⭐⭐⭐ |
| **复杂度** | 低 | 中 | 高 |
| **风险等级** | 🟢 低 | 🟡 中 | 🔴 高 |
| **适用场景** | ... | ... | ... |
```

### Phase 3: 边界分析

识别每种方案的失效模式和边界情况。

### Phase 4: 决策推荐

**输出模板**：
```markdown
### 🎯 推荐决策

**推荐方案**：方案 X

**推荐理由**：
1. ...
2. ...

**关键假设**：
- 假设 1：...
- 假设 2：...

**回退方案**：
如果...失败，切换到方案 Y
```

### Phase 5: 设计文档输出（新增）

**设计确认后，必须执行以下步骤**：

```markdown
1. 生成设计文档
2. 自检（规格完整性检查）：
   - [ ] 是否存在占位符（TODO、TBD、待定）？
   - [ ] 各章节内容是否一致？（比如接口和数据模型是否匹配）
   - [ ] 是否超出了需求范围（范围蔓延）？
   - [ ] 是否每个决策都有理由？
3. 保存到文档目录
4. 提交设计文档
```

**文档保存路径**：
```
docs/plans/YYYY-MM-DD-<功能名称>-design.md
```

**文档头部模板**：
```markdown
# [功能名称] 设计文档

> **日期**: YYYY-MM-DD
> **状态**: [草稿/已评审]
> **对应需求**: [需求描述或 Issue 链接]

---
```

### Phase 6: 行动清单

**输出模板**：
```markdown
### ✅ 行动清单

- [ ] 任务 1：...（预计 X 小时）
- [ ] 任务 2：...（预计 Y 小时）

**总计预计**：X 天
**关键里程碑**：...
```

## 验证检查

每次 brainstorming 完成后，必须验证：

- [ ] 是否遵循了一次一问原则？
- [ ] 是否先探索了代码库？
- [ ] 是否应用了 YAGNI（删除了不必要的功能）？
- [ ] 是否生成了 2-3 个方案？（不是只给一个）
- [ ] 是否提取了所有约束条件？
- [ ] 是否分析了边界情况？
- [ ] 是否将设计文档输出到 `docs/plans/`？
- [ ] 是否提交了设计文档？

---

## 禁止模式

❌ **一次抛一堆问题** —— 必须一次一问
❌ **只给一个方案** —— 必须提供多个选项对比
❌ **跳过约束分析** —— 必须明确约束条件
❌ **只有优点没有缺点** —— 必须诚实分析 trade-off
❌ **设计不落地到文件** —— 必须输出设计文档并提交
❌ **不应用 YAGNI** —— 必须移除不必要的功能
❌ **不了解代码库就开设计** —— 必须先探索
