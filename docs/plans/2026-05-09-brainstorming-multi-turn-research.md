## 4. 多轮交互能力现状

### 4.1 现有机制 ✅

dev-suite 已具备多轮交互能力，通过以下机制实现：

| 机制 | 类型 | 说明 |
|------|------|------|
| **一次一问（brainstorming）** | 技能级 | 每次只问一个问题，等待用户回复后再继续 |
| **AskUserQuestion 工具** | 系统工具 | 结构化多选问题，支持 2-4 个选项 + 多选 |
| **SendMessage 工具** | 系统工具 | Agent 间通信，支持 message/broadcast/shutdown |
| **conversation_search 工具** | 系统工具 | 搜索历史对话，恢复跨会话上下文 |
| **工作记忆（MEMORY.md）** | 持久化 | 跨会话记忆存储，自动注入上下文 |
| **daily log（YYYY-MM-DD.md）** | 持久化 | 每日工作日志，会话恢复 |

### 4.2 一次一问机制详解

`brainstorming` 的「一次一问」是多轮交互的核心实现：

```
传统方式（❌ 不推荐）：
  Agent: "你的预算是多少？技术栈是什么？有没有性能要求？"
  → 用户一次性回答多个问题，容易遗漏

一次一问（✅ 强制）：
  Agent: "你的预算大概是多少？"
  User: "10 万以内"
  Agent: "好的。技术栈有要求吗？（Java/Go/Python...）"
  User: "Java"
  Agent: "明白。有没有特殊的性能要求？"
  → 每次聚焦一个问题，上下文清晰
```

### 4.3 多轮交互的边界

| 能力 | 现状 | 备注 |
|------|------|------|
| 简单多轮（Q&A） | ✅ 完整支持 | 一次一问 + AskUserQuestion |
| 复杂多轮（上下文保持） | ✅ 完整支持 | 会话上下文自动保持 |
| 跨会话记忆 | ✅ 完整支持 | MEMORY.md + daily log |
| Agent 间多轮 | ✅ 完整支持 | SendMessage + TeamCreate |
| 用户中断/恢复 | ✅ 完整支持 | 会话可压缩/恢复 |
| 主动引导对话 | ⚠️ 部分支持 | 依赖技能设计，无通用机制 |

## 5. 差距分析（Gaps）

### 5.1 头脑风暴能力

| 差距 | 影响 | 优先级 |
|------|------|--------|
| **无可视化输出** | 方案对比纯文本，不够直观 | P2 |
| **无决策追溯** | 无法回溯为什么选了方案 A | P1 |
| **无方案评分量化** | 决策矩阵是定性的，缺少量化评分 | P2 |
| **无历史方案库** | 每次重新头脑风暴，无法复用 | P1 |

### 5.2 多轮交互能力

| 差距 | 影响 | 优先级 |
|------|------|--------|
| **无对话状态机** | 复杂多轮场景容易迷失方向 | P1 |
| **无用户意图识别** | 用户中途改变需求时，无法智能调整 | P2 |
| **无对话质量评估** | 无法评估多轮交互是否高效 | P3 |
| **无主动提问策略** | 提问顺序固定，无法动态优化 | P2 |

## 6. 增强建议（Recommendations）

### 6.1 头脑风暴增强（P1）

**建议 1：决策追溯机制**

```
方案选择后，自动生成决策记录：

# 决策记录：XXX 功能

- **选定方案**：方案 B（平衡方案）
- **决策时间**：2026-05-09
- **决策依据**：
  1. 预算限制（10 万以内）→ 排除方案 C
  2. 团队熟悉 Java → 选用 Spring Boot
  3. 性能要求 1000 QPS → 方案 B 满足
- **拒绝的方案**：
  - 方案 A：无法满足扩展性要求
  - 方案 C：超出预算
```

**建议 2：历史方案库**

```
brainstorming/sessions/
├── 2026-05-09-user-auth-design.md
├── 2026-05-08-payment-module-design.md
└── index.md  # 方案索引（按领域分类）
```

### 6.2 多轮交互增强（P1）

**建议 1：对话状态机**

在 `brainstorming` 技能中引入状态机：

```yaml
states:
  - id: "constraint_extraction"
    name: "约束提取"
    next: "scheme_generation"
    timeout: 300  # 5 分钟无输入自动总结
    
  - id: "scheme_generation"
    name: "方案生成"
    next: "boundary_analysis"
    
  - id: "boundary_analysis"
    name: "边界分析"
    next: "decision"
    
  - id: "decision"
    name: "决策推荐"
    next: "document_output"
    
  - id: "document_output"
    name: "文档输出"
    next: null  # 结束
```

**建议 2：用户意图识别**

在 `skill-dev-using` 中新增意图识别规则：

```markdown
## 意图识别增强

当用户在多轮对话中改变需求时：

1. 检测关键词："不对"、"等等"、"其实"、"我想换个"
2. 暂停当前流程
3. 总结已讨论内容
4. 询问用户是否重新开始，还是调整当前方案
```

## 8. 开放问题

1. **「一次一问」是否应该做成通用机制？**
   - 当前只在 `brainstorming` 中强制，其他技能（如 `skill-dev-design`）未强制
   - 建议：在 `skill-dev-using` 元技能中全局强制

2. **多轮交互的「超时」如何处理？**
   - 用户长时间不回复，Agent 应该主动总结还是保持等待？
   - 建议：增加 `timeout` 机制，超时后自动总结并保存进度

3. **历史方案库如何分类？**
   - 按领域？（认证/支付/订单...）
   - 按技术栈？（Java/Go/Vue...）
   - 建议：双重分类，支持按领域 + 技术栈检索

## 9. 结论

| 问题 | 答案 |
|------|------|
| **是否具备头脑风暴的能力？** | ✅ 是，`brainstorming` v2.0.0 已具备完整能力 |
| **多轮交互能力如何？** | ✅ 完整支持，「一次一问」+ 系统工具链 |

**核心优势**：
- 「一次一问」机制强制结构化思考
- YAGNI 原则防止过度设计
- 设计文档强制输出，可追溯

**核心差距**：
- 缺少决策追溯和历史方案复用
- 缺少对话状态机和意图识别

**推荐下一步**：
1. 新增决策追溯机制（P1，2 小时）
2. 引入对话状态机（P1，4 小时）
3. 创建历史方案索引（P1，1 小时）
