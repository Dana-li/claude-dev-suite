# 系统化调试

> **核心铁律：无根因，不修复**

---

## 铁律

> `NO FIXES WITHOUT ROOT CAUSE INVESTIGATION FIRST`

**意思就是：**

1. 遇到 Bug 时，**先花时间找到根因**
2. 不要猜测、不要包 try-catch、不要"先试试"
3. 找到根因之后，**先写一个能稳定复现的测试**
4. **然后**才修复

---

## 4 阶段调试流程

```
发现 Bug / 测试失败 / 意外行为
            │
            ▼
┌───────────────────────────┐
│ Phase 1: 根因调查          │
│ (读错误信息 → 一致重现     │
│  → 检查最近变更 → 收集证据) │
└───────────┬───────────────┘
            │
            ▼
┌───────────────────────────┐
│ Phase 2: 模式分析          │
│ (找正常工作的示例 →         │
│  对比差异 → 理解依赖)       │
└───────────┬───────────────┘
            │
            ▼
┌───────────────────────────┐
│ Phase 3: 假设与验证         │
│ (提出单一假设 →             │
│  最简验证 → 确认根因)        │
└───────────┬───────────────┘
            │
            ▼
┌───────────────────────────┐
│ Phase 4: 修复实现           │
│ (写失败测试 → 实现修复      │
│  → 验证修复 → 输出复盘)      │
└───────────────────────────┘
```

---

## Phase 1: 根因调查

### 步骤

```
1. 读取错误信息
   - 异常类型和堆栈跟踪
   - 错误消息全文
   
2. 一致重现
   - 找到触发条件：输入/操作/环境
   - 确认可以稳定复现（不是偶发）
   - 写一个能稳定触发 Bug 的测试或用例
   
3. 检查最近变更
   - git log --oneline -20（最近的提交）
   - 关联的 PR、Issue
   - 配置变更、数据库变更
   
4. 收集证据
   - 相关日志（WVP 日志、ZLM 日志、应用日志）
   - 请求/响应数据
   - 环境信息（版本、配置）
```

### 输出

```markdown
### 🕵️ 根因调查

| 项目 | 内容 |
|------|------|
| Bug 描述 | [一句话描述] |
| 复现步骤 | 1. ... 2. ... |
| 首次出现 | [提交/日期] |
| 最近变更 | [相关提交] |
| 相关日志 | [关键日志片段] |
```

---

## Phase 2: 模式分析

### 步骤

```
1. 找工作示例
   - 类似功能中正常工作的代码
   - 对比：为什么这个能工作，那个不能？
   
2. 识别差异
   - 配置差异
   - 数据差异
   - 代码路径差异
   
3. 理解依赖
   - 这个功能依赖哪些外部系统？
   - 依赖的状态是否正确？
```

---

## Phase 3: 假设与验证

### 步骤

```
1. 提出单一假设
   - "根因是 X"
   - 一次只验证一个假设
   
2. 最简验证
   - 用最小化的测试验证假设
   - 不是在完整系统上试
   
3. 确认或排除
   - 假设成立 → 进入 Phase 4
   - 假设不成立 → 回 Phase 1 继续调查
```

---

## Phase 4: 修复实现

### 步骤

```
1. 写失败测试
   - 编写能稳定触发 Bug 的测试用例
   
2. 修复根因
   - 修复根本原因，不是包一层 catch
   
3. 验证修复
   - 运行测试确认通过
   - 检查没有引入新问题
   
4. 输出复盘
   - 保存到 docs/bug-fix/
```

---

## 3 次失败规则

> **如果连续 3 次修复尝试都失败了，停止修复。质疑架构。**

这意味着：
- 你一直在错误的方向上找原因
- 这个问题不是简单 Bug，可能是架构问题
- 需要退一步重新理解系统

**此时应该做：**

```
1. 停止当前修复方向
2. 重新完整阅读相关代码
3. 检查系统边界（输入/输出）
4. 检查环境/配置传播
5. 考虑是不是设计层面的问题
```

## 红色警报

以下想法出现时，**必须停止并遵循调试流程**：

| 危险想法 | 正确的做法 |
|----------|-----------|
| "先快速修复一下，稍后再调查" | 先调查，再修复 |
| "试试改 X 看能否工作" | 提出假设，验证，再改 |
| "多个改动一起，运行测试" | 一次只改一处 |
| "跳过测试，我手动验证" | 先写测试 |
| "可能是 X，让我修复一下" | 先验证 X 确实是根因 |
| "我不完全理解但这可能管用" | 先理解，再修 |

## 多组件系统调试提示

当问题涉及多个组件时，在每个组件边界添加诊断：

```
[请求] → [组件 A] → [组件 B] → [组件 C] → [响应]
          │           │           │
          ▼           ▼           ▼
      记录入/出     记录入/出     记录入/出
```

这样能快速定位问题出在哪个组件。
