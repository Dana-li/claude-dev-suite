# 代码审查 —— 两阶段审查循环

> **核心原则：尽早审查，经常审查**

---

## 两阶段审查流程

```
                ┌───────────────┐
                │ 提交审查代码    │
                └───────┬───────┘
                        │
          ┌─────────────▼─────────────┐
          │  Stage 1: 规格合规审查      │
          │  (代码是否符合需求规格？)     │
          └─────────────┬─────────────┘
                        │
              ┌─────────▼──────────┐
              │     是否通过?       │
              └────┬──────────┬────┘
                   │ 是       │ 否
                   │          ▼
                   │   ┌─────────────┐
                   │   │ 创建修复Agent│◄──── 自动重试
                   │   │ 修复规格差距  │
                   │   └──────┬──────┘
                   │          │
                   └──────────┘
                        │
          ┌─────────────▼─────────────┐
          │  Stage 2: 代码质量审查      │
          │  (可读性/性能/安全/约定?)    │
          └─────────────┬─────────────┘
                        │
              ┌─────────▼──────────┐
              │     是否通过?       │
              └────┬──────────┬────┘
                   │ 是       │ 否
                   │          ▼
                   │   ┌─────────────┐
                   │   │ 创建修复Agent│◄──── 自动重试
                   │   │ 修复质量问题  │
                   │   └──────┬──────┘
                   │          │
                   └──────────┘
                        │
          ┌─────────────▼─────────────┐
          │  审查完成: 输出审查报告    │
          └───────────────────────────┘
```

---

## Stage 1: 规格合规审查

**目标**：确认代码实现**与原始需求/设计规格一致**

### 审查要点

| 检查项 | 说明 |
|--------|------|
| ✅ **功能完整性** | 所有需求点是否都已实现？ |
| ✅ **范围边界** | 是否超出了需求范围（过度构建）？ |
| ✅ **接口一致** | API 签名、返回类型是否匹配规格？ |
| ✅ **异常处理** | 规格中定义的异常场景是否都覆盖了？ |
| ✅ **数据模型** | 字段定义、约束是否与设计一致？ |

### 审核未通过时

自动创建修复 Agent，执行：

```
1. 读取审查报告的差距列表
2. 逐一修改代码填补差距
3. 重新提交审查
4. 循环直到 Stage 1 通过
```

---

## Stage 2: 代码质量审查

**目标**：检查代码的可读性、性能、安全性和工程约定

### 审查维度

| 维度 | 权重 | 检查项 |
|------|------|--------|
| **正确性** | 30% | 逻辑正确、空指针、边界条件、并发安全 |
| **安全性** | 25% | SQL 注入、XSS、越权、敏感数据泄露 |
| **可读性** | 20% | 命名规范、注释清晰、函数长度、代码风格 |
| **性能** | 15% | N+1 查询、缓存命中、循环效率 |
| **可维护性** | 10% | 耦合度、重复代码、测试覆盖、设计模式 |

### 输出格式

```markdown
# 代码审查报告

## 概述
- 审查范围：[文件/目录]
- 审查阶段：Stage 2（代码质量）
- 发现问题：X 个
  - 🔴 **Critical**：X（必须立即修复）
  - 🟡 **Important**：X（继续前必须修复）
  - 🔵 **Minor**：X（稍后处理）

## 问题详情

### 🔴 Critical 问题

| # | 位置 | 问题 | 建议修复 |
|---|------|------|----------|
| 1 | [文件:行号] | [描述] | [方案] |

### 🟡 Important 问题

| # | 位置 | 问题 | 建议修复 |
|---|------|------|----------|
| 1 | [文件:行号] | [描述] | [方案] |

### 🔵 Minor 问题

| # | 位置 | 问题 | 建议修复 |
|---|------|------|----------|
| 1 | [文件:行号] | [描述] | [方案] |

## 总结
[审查总结]
```

## 严重性分级与行动要求

| 级别 | 标记 | 行动要求 |
|------|------|----------|
| **Critical** | 🔴 | **必须立即修复** — 编译器错误、安全漏洞、SQL 注入、数据丢失风险 |
| **Important** | 🟡 | **继续前必须修复** — 逻辑错误、性能瓶颈、代码规范违反 |
| **Minor** | 🔵 | **稍后处理** — 风格偏好、非关键建议、可选的改进 |

---

## 如何推回错误反馈

如果审查者的建议不正确，可以使用技术理由推回：

| 推回理由 | 说明 |
|----------|------|
| 建议破坏现有功能 | 改了这处会导致已有的某功能失效 |
| 审查者缺乏完整上下文 | 这个设计的背后有特定的业务约束 |
| 违反 YAGNI | 建议引入的抽象在当前场景下不需要 |
| 技术栈不匹配 | 这个建议对这个语言/框架不适用 |
| 存在遗留兼容性原因 | 为了向后兼容必须保持这个写法 |
| 与架构决策冲突 | 这个项目的架构已经决定了不同的方向 |

> ⚠️ 推回时必须有技术依据，不能因为"懒得改"

## 审查范围

### Java/Spring Boot
- 代码规范（命名、注释、格式）
- 安全漏洞（SQL注入、XSS、越权）
- 性能问题（N+1查询、循环查询）
- 异常处理
- 日志规范

### Vue/前端
- 组件设计
- 响应式规范
- 状态管理
- 性能优化
- 安全最佳实践
